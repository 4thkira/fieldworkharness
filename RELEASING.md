# Releasing Fieldwork

Fieldwork publishes prereleases through GitHub Releases at
[`4thkira/fieldworkharness`](https://github.com/4thkira/fieldworkharness). It is not published to the
npm registry: `package.json` stays `"private": true`. The `.tgz` attached to a release is an
installable inspection artifact, not a registry package.

This checklist does not authorize a public push or release. Stop for the maintainer's explicit
approval at the publication boundary.

## Release contract

- Versions follow SemVer prerelease syntax. The first public candidate is `0.1.0-alpha.1`.
- A GitHub prerelease keeps the source archives generated by GitHub plus the checked `.tgz`, source
  archive, `SHA256SUMS.txt`, release manifest, and notes for that exact version.
- Public history begins with one new root commit made from the reviewed private tree. Never add the
  private repository as a remote, copy its `.git` directory, use a worktree, or push its objects.
- Release artifacts are built from the verified public commit, outside either source repository.
- The Fieldwork community guidelines apply in official project spaces without policing private local
  adult use. Vulnerabilities and sensitive community reports use GitHub's private reporting route;
  enable and verify it before publication.

## 1. Prepare the private source tree

Start from the intended release commit with a clean worktree. Confirm the version, release notes,
changelog, security policy, code of conduct, licence files, and documented limitations all describe
the same candidate. Install and run both gates:

```sh
npm ci --no-fund --no-audit --ignore-scripts
npm run check
npm run release:check
```

The gates verify source behavior and the bounded npm-shaped archive. They do not prove a browser
engine, uploaded asset, live bridge, or public repository setting.

## 2. Create a history-clean public repository

Choose a new, nonexistent destination outside this repository. The exporter never replaces a
caller-owned path. Supply the public maintainer identity explicitly:

```sh
npm run release:prepare-public -- --destination /absolute/path/to/fieldworkharness-public --author-name 4thkira --author-email 143560680+4thkira@users.noreply.github.com --message "Initial public release v0.1.0-alpha.1"
```

The exporter reconstructs the exact tracked tree from Git objects, initializes a repository with no
templates, hooks, remotes, alternates, or inherited Git identity, and creates exactly one root commit.
It refuses a dirty or changing source. It never pushes. Preserve its receipt only in the private
release record: `sourceHead` identifies a private commit and must never be attached, committed to the
public snapshot, or pasted into the public release.

In the new repository, independently confirm:

```sh
git rev-list --count HEAD
git rev-list --parents --max-count=1 HEAD
git status --short
git remote -v
git fsck --full --strict --no-reflogs --unreachable
npm ci --no-fund --no-audit --ignore-scripts
npm run check
npm run release:check
```

The commit count must be `1`; the commit line must name no parent; status, remotes, and unreachable
objects must be empty. Compare `HEAD^{tree}` with the private release commit's tree. Scan the complete
tracked public source for credentials, personal paths, private names, transcripts, profiles, and
assets—not only the npm archive.

## 3. Verify the packaged candidate

From the clean public repository, build into a new directory outside the repository:

```sh
npm run release:build -- --output-root /absolute/path/to/fieldwork-release-artifacts
```

Verify every entry in `SHA256SUMS.txt`, inspect the manifest and archive contents, and retain the
build receipt. Then run the packaged candidate in a real supported browser. At minimum:

1. Finish first-run bootstrap with synthetic data.
2. Open Settings with the keyboard.
3. Send and stream one synthetic reply.
4. Rename, archive, and restore a conversation.
5. Confirm keyboard focus remains visible at larger text scales.
6. Confirm the browser console has no unexplained warning or error.

Keep browser/platform evidence separate from source-test evidence. Do not configure a real bridge,
provider credential, profile, or transcript for release QA.

## 4. Prepare the GitHub boundary

Before any push:

1. Confirm `https://github.com/4thkira/fieldworkharness` is still the intended empty public repository.
2. Enable private vulnerability reporting in repository security settings and verify the private
   advisory form opens for the maintainer.
3. Add that URL as `origin` only in the new one-root public repository.
4. Fetch or query the remote and confirm it has no refs.
5. Review the exact root commit, tree ID, version, artifact hashes, notes, and proposed tag.
6. **Stop for explicit maintainer approval.** Do not infer permission from an existing repository,
   local remote, completed checks, or this document.

## 5. Publish after approval

After explicit approval, push only the public repository's `main` branch. Verify the hosted commit and
CI before creating the signed or annotated `v0.1.0-alpha.1` tag. Push the tag, create a GitHub
**prerelease**, paste the reviewed notes from `docs/releases/0.1.0-alpha.1.md`, and attach only the
artifacts produced from that hosted commit.

After upload, compare the downloaded `SHA256SUMS.txt` byte-for-byte with the retained, locally verified
copy, then verify every attachment it lists. Confirm the security-reporting route still works and that
no npm package was published. If the candidate changes at any point, discard its artifacts and repeat
every gate on the new commit.
